# Changelog

Chronological, newest entries first. Each item records the date, goal, and files.

## 2026-11-02

- **Minimum systems macOS 14 and iOS 17 (macOS target set in one place):** before, the Mac binary got the minimum system of the building Mac (`minos 26.0` on Tahoe, 15.5 for the Objective-C parts with Xcode 16.4), the macOS shader libraries were pinned to `air64-apple-macos26.0` (AIR v28, which macOS 14 and 15 probably cannot load; not tested), and `LSMinimumSystemVersion` and the icon compiler said 13.0. Now `BDSP_MACOS_MIN=14.0` in `scripts/recomp/macos_target.sh` feeds `-mmacosx-version-min` for the guest objects (`compile_chunk.sh`), the runtime, the NVN/Metal layer and the link (`runtime/build.sh`, `nvn/build_nvn.sh`), the AIR target (`shader_bin.sh`, now `air64-apple-macos14.0`), `LSMinimumSystemVersion` (`Info.plist.in`, filled in by `make_app.sh`) and `icon_composer.py`; iOS stays 17.0. The binary reports `minos 14.0`, the libraries `air64_v26-apple-macosx14.0.0` (Xcode 27.1) or `air64-apple-macosx14.0.0` (Xcode 16.4). The file is part of the stage hash, the object signatures and the shader bootstrap stamp, and the runtime and NVN object folders carry a target stamp, so old objects (host minos) and old libraries (macOS 26) are rebuilt once; the first rebuild after this change recompiles the guest objects (about 6 minutes on 8 threads). New `scripts/recomp/availability_check.sh` (run by `scripts/check.sh`) compiles the runtime and the iOS app sources for macOS 14 and iOS 17 with `-Wunguarded-availability-new -Wpartial-availability` and fails on any unguarded newer API: against the SDKs of Xcode 27.1 (macOS 27.0, iOS 27.1) and Xcode 16.4 (macOS 15.5, iOS 18.5) it reports none, so no guard was needed. All 2739 game shaders and the embedded Metal sources compile for `macos14.0` with both Xcode versions. Built with both and started on macOS 26.6: all prebuilt libraries load, no Metal API or shader validation message. Not checked: macOS 14/15 and iOS 17/18 hardware. The Homebrew libraries (SDL3, FFmpeg) keep the minimum of the building Mac (26.0 here) and make the linker warn; with Xcode before 26 the apps get the classic icon (see the Xcode 16 entry), since `actool` before Xcode 26 cannot compile Icon Composer documents. Docs: `BUILD.md`, `BUILD.de.md`, both READMEs, `recomp-icons.md`, `recomp-ios.md`, `shaders.md`.
- **Installer shows what it is doing (progress view):** every stage card has an activity line ("Unpacking the game container", "Verifying the game files (SHA-256)", "Translating shaders", "Compiling objects: n of m", "Linking the game executable", ...) in five languages, "Step n of 5" for Prepare game, and "Still working: ..." with the time in the step after 15 s without a backend event (`installer/src/activity.rs`, `progress.rs`, `app/view.rs`). It is derived from the existing steps, counters and log lines, so no protocol change: the Rust parser of released installers rejects unknown event types, so only log lines and existing fields are used. `driver.py` reports the shader counter per phase (translated shaders while translating, libraries of translated shaders while compiling); the Windows pipeline streams the extract tool's output; the extract tool logs its silent SHA-256 phases.
- **Windows path length is checked before the build (issue 28, not closed):** the generator reports a too long path as "cannot create output file (No such file or directory)" in the middle of a build. `scripts/install/pathlimits.py` plans the longest path below the work folder (about 157 characters, more with deep game folders), the Windows preflight stops with "The install folder is too deep for Windows (N of 260 characters)" when work folder plus that reaches 260 and `LongPathsEnabled` is off, and the build checks again after the extraction with the real `romfs` paths. With long paths on, the build starts with a note (the build tools were not checked for long path support). The diagnostics block carries the `Path length check:` line. Tests: `scripts/tests/test_pathlimits.py`, `test_windows_pipeline.py`.
- **System report in the installer log:** `scripts/install/diagnostics.py` (stdlib only, runnable alone) writes `[Diagnostics]` lines at the start of a build: OS, hardware, GPU and driver, disk, path length, tools, Windows long paths and Defender state. Redacts user, home, host, serials, MAC, IP, UUIDs; no network. Opt out with `BDSP_NO_DIAGNOSTICS=1`. Docs: `BUILD.md` 8.1. Tests: `scripts/tests/test_diagnostics.py`, `test_installer_driver.py`.
- **Window title is the game's name in the system language:** `Pokémon Strahlender Diamant` on a German system, `Pokémon Brilliant Diamond` on an English one (Diamond or Pearl and every language come from the dump's control.nacp), then ` - <mod>` and ` [<BDSP_WINDOW_TAG>]`. Before, the windows said "BDSP" or "BDSP Recomp". `game_icons.py` writes `titles.json` next to `icons.json` (also for mod builds, which keep the game's names there); `runtime/window_title.c` is the one place that matches the system language list to the NACP locales and composes the title for the Mac app, the SDL/Vulkan window and the Qt host. The Mac app ignores `-AppleLanguages <value>` and other `-NS*`/`-Apple*` pairs instead of exiting. Test: `scripts/recomp/runtime/test/run_window_title_test.sh` (also in `scripts/check.sh` and the Python suite). Docs: `recomp-icons.md`, `BUILD.md`, `mods.md`.
- **Mods on Windows (#27):** the Windows build no longer stops at step 11 with "Mod installation is not wired to the native Windows package yet". The driver validates the selected mod once for every target (`_selected_mod`) and stages IPS/IPS32 and `subsdk1` with the installer's `ips_patch` for every target that has a separate mod app (`_prepare_code_mod`, no Apple-only allow list). `windows_pipeline.build_game` builds a code mod from the staged ExeFS in `work/recomp/mods/<key>`, links a RomFS-only mod app on the game's compiled code, and installs `BDSP-<name>-<id>` beside the game with a `mod.txt` (mod name, mods folder, `romfs`/`exefs`) that `win32_entry.c` turns into `BDSP_MOD`/`BDSP_MODS_DIR`/`BDSP_COMPILED_EXEFS`. The GUI allows IPS/IPS32 mods on Windows (`ips_target`). Without UnityPy (Windows runtime) the mod icon falls back to the MOD badge with a log line. Linux ExeFS stays refused with the exact reason (one fixed app and launcher). Tests: `test_windows_pipeline.py`, `test_game_icons.py`, `test_windows_native_generator.py` (mod.txt), `app.rs`. Real build on Windows 11 with Luminescent Platinum 2.2F: see `docs/mods.md`.
- **Export IPA with embedded data: transparency and no silent fallback:** the log says before the build and when the IPA is written that the IPA is exported WITH the game data (about 5.3 GB, minutes, own devices only, do not share, how to export without data); the write is named in three steps with progress for the zip and the hash; the result gives path, size and "no Game Library needed". Too little space stops the export with needed and free GB and the explicit switch `--ios-export-no-embed`; nothing switches to an export without data by itself (tests in `test_ipa_embed.py`). Installer 0.1.4: the review page shows the warning and the visible switch "Export without game data" before the start, the finished page names path, size and WITH/WITHOUT game data (and a missing Game Library). READMEs updated. Not run on a device; the 0.1.3 GUI shows the log lines, how it renders them was not looked at.
- **Export IPA embeds the game data (default):** the IPA contains the RomFS (and the `romfs`/`exefs` folders of a mod) of the user's own dump below `res/EmbeddedData`, so a sideloaded IPA runs without a Game Library. Only the IPA export does this; the direct installation still copies the data with `devicectl`. New driver switch `--ios-export-no-embed` (and the build option "Export without game data" of the 0.1.4 GUI) gives the former export; installers without the switch export the new way, because the default needs no argument. `installer_build.sh package` clears and re-embeds before the ad hoc signature; `scripts/install/ipa_pack.py` writes the IPA once (ZIP64, embedded files stored, named by its SHA-256) with `progress` events; `res/install-data.plist` gets `EmbeddedLibrary`, saves keep the exported-app layout. The app reads the bundle as a verified library (`data_manager.m`: full check once with a receipt in `Library/Caches`, then metadata; "Check game files again" repeats it). The log and docs say that such an IPA is for the owner's devices only. Measured with the real 4.7 GB RomFS: IPA 5.30 GB, 20,583 files, package step 80 to 90 s, IPA written and hashed in 29 s. Tests: `scripts/tests/test_ipa_embed.py`, `test_data_store.m` (bundle source). Not run on a device. Docs: `installer/docs/ios-delivery.md`.
- **iPhone/iPad: an IPA without game data no longer reaches the runtime silently:** `startGame` refuses while the data are not verified (unknown counts as not verified), `StartSelectedRuntime` checks `Data/` once more before the runtime thread starts (it only logged a warning before), and an inventory without RomFS files is rejected when created and when verified. A quick pre-check without hashing (`BDSPInspectData`, `BDSPInspectLibrary`) names the problem (folder missing, empty, files of length 0, files missing, with the count) and the dialogs in en, de, es, pt and ru say that an IPA never contains game data, with a Help button (`data_manager.m`, `data_library.m`, `app.m`). The runtime stops through `rt_fatal` when the RomFS folder holds no files and logs the first unreadable file (`services_fs.c`). Tests: `test_data_store.m` (`scripts/tests/run_ios_data_tests.sh host`), `runtime/test/romfs_test.c`. Not run on a device. Docs: `installer/docs/ios-delivery.md` ("An IPA alone does not run", with the design of an experimental embedded-data export, not built), READMEs.
- **Xcode 16 builds the apps (issue #29, builds on PR #30 by chasem-dev):** the app icons were compiled from Icon Composer documents, which
  the `actool` of Xcode 16 skips without an error, so the macOS build ended in the package step with a missing `BDSP_<hash>.icns`.
  #30 adds the check (`actool_version()`, `compile_icons` verifies its outputs, preflight entry). On top of it: Xcode before 26 is a
  preflight note, not a missing program, and the builders fall back to a classic icon (macOS: `.iconset` through `iconutil`; iPhone/iPad:
  loose icon PNGs plus `CFBundleIcons` keys, no actool) when `actool` is before 26 or unreadable; `BDSP_LEGACY_ICONS=1` forces it. No Liquid Glass
  there. Files: `build_stages.py`, `app/icon_composer.py`, `app/game_icons.py`, docs. Checked with Xcode 16.4 (macOS 15.5 SDK, iOS 18.5 SDK):
  full macOS build to a running app with the classic icon; the iOS runtime sources compile against the iOS 18.5 SDK; the iOS icon files
  go into a real app bundle, which was signed and zipped to an IPA. Not checked: running on a device.
- **Starter selection crash (issue #24), runtime:** the loader entered text and rodata of each module with their unrounded ends, so
  `QueryMemory` showed a free gap between text, rodata and data. The SDK's `nn::ro::detail::GetExceptionInfo` walks that map on every
  C++ throw and aborted (`svcBreak`) at the gap; choosing the starter throws one (DOTween in `RectTransform.get_anchoredPosition`). The
  segments now end on page boundaries (`loader.c`, test in `runtime/test/code_mod_test.c`). A `svcBreak` from that path now logs the
  throwing frame and the module memory map (`kernel.c`). Unmodified game on the Mac, Turtwig chosen with Yes and the first battle
  played: before, 2 of 2 runs crashed (svcBreak at Yes; once the render worker crash below, before the Yes); after, 8 of 8 clean
  (2 of them with `MTL_DEBUG_LAYER` and `MTL_SHADER_VALIDATION`, no validation message).
- **Render worker (Metal):** texture and program release wait for the render worker by default (was iOS only), as its command lists
  point at those objects; freed textures (`0x0x0`, format 0) reached the pipeline compiler as colour targets (`renderer.m`, `metal.m`,
  `objects.c`). Colour targets Metal cannot render to are left out with a log line, and pipeline records with such formats are refused
  instead of aborting in Metal's validation. `BDSP_XW_DRAIN_DESTROY=0` restores the old behaviour.
- **Linux aarch64 unlocked as experimental (issue 23):** the graphical installer (`backend_supported` in `installer/src/app.rs`, now `platform_backend_supported`) and `install-linux.sh` stopped refusing aarch64 on purpose; both claimed AVX2 was needed, but the build uses `-march=native` or `-mcpu=native` and needs no AVX2. The GUI and the script show an experimental notice (five and four languages). `install-linux.sh` finds the Qt Wayland plugin in any multiarch folder (`/usr/lib/$(uname -m)-linux-gnu/qt6`) and under its Qt 6.8 name `libqwayland.so`; new test hook `BDSP_INSTALL_ARCH`. The Vulkan backend converts BC textures to ASTC 4x4 / R8 / RG8 on GPUs without BC (`bctc.c`, `BDSP_TEST_NO_BC=1`; `textures.c`, `build_vk.sh`, `portable_build.py`). Tests: `scripts/tests/test_linux_install.py`, `app.rs` support matrix. Docs: `BUILD.md` 6.5, `BUILD.de.md`, READMEs.
